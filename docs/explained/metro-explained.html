دليل مشروع المترو

شرح المشروع كله، من غير ما تكون عارف أي حاجة في البرمجة. نظام إدارة مترو مكتوب بلغة Java — مشروع رقم ٨ في مادة Programming Language 2.

ازاي تقرا الدليل ده

الدليل متقسم زي خط المترو: محطات ورا بعض. كل واحد في الفريق يقرا أول ٦ محطات (لحد "مين يقدر يعمل إيه")، وبعدين يقرا الجزء بتاعه كويس جدًا، وبعدين "يوم المناقشة".

  • الكلام عربي، بس أسماء الحاجات في الكود سبناها إنجليزي زي ما هي، زي Station و Ticket، عشان الدكتور هيسألك بيها.
  • جنب كل فكرة مهمة فيه صندوق أزرق مكتوب فيه جملة بالإنجليزي. دي الجملة اللي تقولها للدكتور لو سألك.
  • كل جزء فيه "لو الدكتور سألك": أسئلة متوقعة وإجاباتها.
  • لو حابب تقرا نفس الكلام بالإنجليزي بتفاصيل أكتر: فيه ملف لكل جزء في docs/modules/ على GitHub.
مش لازم تحفظ الكود. المطلوب إنك تفهم كل كلاس في جزءك بيعمل إيه وليه، وتعرف تفتحه وتشاور على المكان اللي فيه الفكرة. ده اللي عليه الـ ٥ درجات الفردي.

المشروع بيعمل إيه؟

تخيل إنك شغال في مترو القاهرة. فيه ناس كتير شغالة، وكل واحد له شغل مختلف:

الشخصفي البرنامج اسمهبيعمل إيه
مدير النظامAdminبيضيف المحطات والخطوط والقطارات، وبيعمل حسابات الموظفين، وبيشوف التقارير والفلوس. يقدر يعمل كل حاجة.
مسؤول التشغيلOperations controllerبيعمل جدول الرحلات: القطر ده يطلع الساعة كام ويوصل الساعة كام، ويسجل التأخير والإلغاء.
موظف الشباكTicket agentبيبيع التذاكر وبيتأكد من التذكرة على البوابة.
مشرف المحطةStation supervisorنفس شغل موظف الشباك، وكمان يقدر يرجّع فلوس التذكرة (refund).

البرنامج بيخلي كل واحد يدخل باسم المستخدم والباسورد بتوعه، ويشوف بس الحاجات المسموح له بيها. البيانات كلها (المحطات، التذاكر، الرحلات...) بتتحفظ في ملفات نصية عادية جوه فولدر اسمه data، فلو قفلت البرنامج وفتحته تاني تلاقي كل حاجة زي ما هي.

البرنامج جاهز ومعاه بيانات تجريبية حقيقية: مترو القاهرة بـ ٨٤ محطة (بالعربي والإنجليزي) على الخط الأول والتاني والتالت وفرع جامعة القاهرة، و١٢ قطر، وأسبوع رحلات، وأسبوع تذاكر مبيوعة.

البرمجة من الصفر

قبل ما نتكلم عن المشروع، محتاجين نتفق على شوية كلمات. هنمشي واحدة واحدة، وكل كلمة بمثال من المشروع بتاعنا.

البرنامج يعني إيه؟ و Java إيه؟

البرنامج = مجموعة أوامر مكتوبة بالترتيب، الكمبيوتر بينفذها. زي وصفة أكل: "حط مية، ولّع النار، استنى لما تغلي".

Java = اللغة اللي كتبنا بيها الأوامر دي. بنكتب الكود في ملفات آخرها .java، وبعدين برنامج اسمه compiler بيحولها لحاجة الكمبيوتر يفهمها، وبعدين الـ JVM بيشغلها. مشروعنا فيه ١١٦ ملف Java.

JavaFX = مكتبة جوه Java بنرسم بيها الشاشات: الزراير والجداول والخانات اللي بتكتب فيها. الكلية طالبة GUI (واجهة رسومية) ولو مش موجودة بيتخصم ٥ درجات — وإحنا عاملينها.

الكلاس والأوبجكت (Class و Object)

دي أهم فكرة في المادة كلها. فكر في استمارة فاضية مكتوب فيها: "اسم المحطة: ___ ، الاسم بالعربي: ___ ، مفتوحة ولا مقفولة: ___". الاستمارة الفاضية دي هي الكلاس.

لما تملا الاستمارة: "حلوان ، حلوان ، مفتوحة" — النسخة المليانة دي اسمها أوبجكت. وممكن تملا استمارات تانية: "السادات"، "عتبة"... كلهم أوبجكتس من نفس الكلاس.

public class Station {          // the blank form: what every station has
    private String name;            // "Helwan"
    private String nameAr;          // "حلوان"
    private StationStatus status;   // OPEN or CLOSED
}

Station helwan = new Station("STN-001", "Helwan", "حلوان", StationStatus.OPEN);  // one filled-in form
public class Station = بنعرّف استمارة جديدة اسمها Station.
private String name = خانة في الاستمارة اسمها name، فيها كلام (String = نص).
new Station(...) = املا استمارة جديدة بالبيانات دي. كلمة new معناها "اعمل أوبجكت جديد".
A class is the design or template; an object is one real instance made from it. Station is the class, Helwan is an object.

الخانات والأفعال (Fields و Methods)

Field = خانة بيانات جوه الأوبجكت (الاسم، الحالة). Method = حاجة الأوبجكت يعرف يعملها أو يجاوب عليها. مثلًا المحطة تعرف تجاوب "انتي مفتوحة؟":

public boolean isOpen() {
    return status == StationStatus.OPEN;   // true if open, false if closed
}
boolean = الإجابة يا "true" (أيوه) يا "false" (لأ).
return = رجّع الإجابة دي للي سألك.

الـ Constructor

ده method خاص بيشتغل مرة واحدة لحظة ولادة الأوبجكت، عشان يملا الخانات ويتأكد إنها صح. اسمه نفس اسم الكلاس.

public Station(String id, String name, String nameAr, StationStatus status) {
    super(id);          // give the id to the parent class (Entity)
    setName(name);      // checks the name is not empty
    setNameAr(nameAr);
    setStatus(status);
}

الـ Enum

قايمة اختيارات ثابتة مش هتتغير. حالة المحطة يا مفتوحة يا مقفولة، ومفيش حاجة تالتة:

public enum StationStatus { OPEN, CLOSED }

في المشروع عندنا enums كتير: حالة القطر (Active / In maintenance / Retired)، حالة الرحلة (Scheduled / Delayed / Completed / Cancelled)، نوع التذكرة (Standard / Student / Senior)، الأدوار، والصلاحيات.

القايمة (List)

لما نحتاج نشيل حاجات كتير من نفس النوع: الخط بيشيل قايمة محطات بالترتيب. List<Station> معناها "قايمة كل عنصر فيها محطة". و ArrayList هو نوع القايمة اللي بنستخدمه.

if و for

if = "لو الشرط ده صح، اعمل كذا". for = "كرر الكلام ده على كل عنصر في القايمة".

for (Station station : stations.findAll()) {        // go over every station, one by one
    if (station.getName().equalsIgnoreCase(name)) {  // same name, ignoring capital letters?
        return station;                              // found it
    }
}
return null;   // went over all of them and found nothing

الـ Exception (الإنذار)

لما حد يحاول يعمل حاجة غلط (يضيف محطة من غير اسم، يبيع تذكرة لمحطة مقفولة)، الكود "بيرمي إنذار" بكلمة throw. الإنذار بيطلع لفوق لحد ما الشاشة "تمسكه" وتعرض رسالته للمستخدم في شريط أحمر — البرنامج عمره ما بيقفل فجأة.

if (name == null || name.isBlank()) {
    throw new ValidationException("Station name is required");
}

عملنا عيلة إنذارات خاصة بينا، كلها طالعة من MetroException: غلطة في البيانات (ValidationException)، مش لاقي حاجة (NotFoundException)، مش مسموح لك (AccessDeniedException)، ملف بايظ (DataFileException)، وقطر في رحلتين في نفس الوقت (ScheduleConflictException).

الاختبارات (Tests)

ده كود تاني بيجرب الكود الأصلي ويتأكد إنه بيدي النتيجة الصح. مثلًا اختبار بيقول: "بيع تذكرة طالب بسعر أصلي ٨ جنيه — لازم تطلع ٤ جنيه". عندنا ٢٨٩ اختبار وكلهم شغالين. ده بيطمنك إن أي حاجة الدكتور هيجربها هتشتغل.

الـ OOP بالبلدي

OOP يعني Object-Oriented Programming: إنك تبني البرنامج من أوبجكتس، كل واحد مسؤول عن نفسه. الكلية حاطة عليها ٥ درجات، والدكتور هيسأل عن ٥ أفكار. هنا كل فكرة بمثال من مشروعنا:

١. Encapsulation — التغليف

الخانات private: محدش من بره يقدر يلمسها مباشرة. اللي عايز يغيرها لازم يعدي على method بيتشيك الأول. زي الخزنة: مش بتمد إيدك جواها، بتطلب من الصراف.

مثالنا: المستخدم مالوش setId خالص، فالـ ID مستحيل يتغير — وده بالظبط طلب الكلية 5b.

٢. Inheritance — الوراثة

كلاس "ابن" بياخد كل حاجة من كلاس "أب" ويزود عليها، بكلمة extends.

مثالنا: مشرف المحطة StationSupervisor extends TicketAgent: بياخد كل صلاحيات موظف الشباك ويزود عليها صلاحية الإرجاع.

٣. Polymorphism — تعدد الأشكال

نفس السؤال، وكل أوبجكت يجاوب بطريقته. اللي بيسأل مش محتاج يعرف هو بيكلم مين.

مثالنا: بنسأل أي تذكرة getFare() "سعرك كام؟" — العادية تقول السعر كامل، الطالب تقول النص، كبير السن تقول ٧٠٪.

٤. Abstraction — التجريد

كلاس "ناقص" معمول عشان يتورث بس، مينفعش تعمل منه أوبجكت (abstract). أو interface: وعد بقايمة أفعال من غير تفاصيل.

مثالنا: Ticket كلاس abstract: مفيش حاجة اسمها "تذكرة وخلاص"، لازم تبقى عادية أو طالب أو كبير سن.

٥. Relationships — العلاقات

إزاي الأوبجكتس مربوطة ببعض: Association (بيستخدم بعض)، Aggregation (بيشيل حاجات ليها حياة لوحدها)، Composition (الجزء بيموت لو الكل مات).

مثالنا: الرحلة مرتبطة بقطر وخط (association). الخط بيشيل محطات، والمحطة ممكن تبقى على خطين (aggregation). المشوار مكون من أجزاء (composition).

Encapsulation hides data behind methods; inheritance reuses a parent class; polymorphism lets the same call behave differently per object; abstraction defines what without how; relationships connect objects.

في كل جزء تحت هتلاقي الـ ٥ أفكار دول جوه الكلاسات بتاعتك أنت، عشان تقدر تشرحهم من شغلك.

المشروع من جوه: مطعم بـ ٤ أدوار

فكر في البرنامج كمطعم. كل دور له شغلانة واحدة، ومحدش بيعمل شغل التاني:

الجرسون = الشاشاتفولدر ui. بياخد طلبك (الزرار اللي دوست عليه) ويوريك النتيجة. مبيطبخش ومبيقررش حاجة.
←
الشيف = القواعدفولدر service. هنا كل القواعد: ينفع ولا لأ؟ مسموح لك ولا لأ؟ السعر كام؟
←
أمين المخزن = الحفظفولدر repository. هو الوحيد اللي بيكلم الملفات: يقرا ويكتب.
←
الرفوف = الملفاتفولدر data. ملفات txt فيها البيانات سطر سطر.

وفيه فولدر خامس اسمه model: دي "الحاجات" اللي الكل بيتكلم عنها — المحطة، الخط، القطر، الرحلة، التذكرة، المستخدم. زي الأطباق في المطعم: الجرسون بيشيلها والشيف بيعملها والمخزن بيخزنها.

ليه كده؟ لو كل حاجة متقسمة، الغلط بيبقى سهل تلاقيه، وتقدر تختبر القواعد من غير ما تفتح شاشة. وكمان ده بيخلي كل واحد في الفريق ماسك حتة واضحة.

رحلة ضغطة زرار: بيع تذكرة

  1. موظف الشباك يختار "من حلوان" و"لجامعة القاهرة" ويدوس Sell في شاشة SellTicketScreen (الجرسون).
  2. الشاشة بتنادي ticketService.sell(...) (الشيف).
  3. الشيف يسأل الأول: "اللي داخل ده مسموح له يبيع؟" عن طريق session.require(SELL_TICKETS).
  4. يتأكد إن المحطتين مفتوحين، ويطلب من RoutePlanner أقصر طريق: ٢٢ محطة، تغيير في السادات.
  5. يجيب السعر من جدول الأسعار: ٢٢ محطة = ١٥ جنيه. ويطلع التذكرة بنوعها.
  6. يدي التذكرة لأمين المخزن TicketRepository اللي بيكتبها سطر جديد في tickets.txt.
  7. الشاشة ترسم كارت التذكرة بالكود بتاعها، زي التذكرة المطبوعة.

ازاي البيانات بتتحفظ

كل نوع بيانات له ملف نصي لوحده في فولدر data. كل سطر = حاجة واحدة، والخانات مفصولة بعلامة |. ده ملف المحطات:

STN-002|Ain Helwan|عين حلوان|OPEN

# id|name|... = أسماء الخانات، للبني آدم اللي بيقرا الملف بس. البرنامج بيتجاهل أي سطر أوله #.

٣ حاجات ذكية في الحفظ

  • مفيش ضياع بيانات: وإحنا بنحفظ، بنكتب ملف مؤقت الأول، وبعدين نبدله بالأصلي مرة واحدة. لو الكهربا قطعت في النص، الملف القديم سليم.
  • أي كلام يتحفظ صح: لو حد كتب | جوه اسم، بنحط قبلها علامة \ عشان البرنامج يفهم إنها جزء من الاسم مش فاصل. والعربي بيتحفظ عادي (UTF-8).
  • لو ملف باظ: البرنامج مبيقفلش فجأة. بيطلع رسالة تقولك اسم الملف ورقم السطر البايظ.
Each record type has its own text file, one record per line, fields separated by a pipe. We save to a temporary file first and then replace the real one, so a crash never leaves half a file.

مين يقدر يعمل إيه

فيه ١٤ "صلاحية" (Permission)، وكل دور معاه مجموعة منهم. القايمة اللي على الشمال في البرنامج بتتبني حسب الصلاحيات دي:

الحماية على مرتين

  1. القايمة بتخبي: الـ agent مش هيشوف زرار التقارير أصلًا.
  2. الشيف بيرفض برضه: حتى لو حد قدر يوصل للزرار بأي طريقة، كل method في الـ service بيبدأ بسطر session.require(...) اللي بيرفض ويقول "You do not have permission to do this."
Authorization is enforced twice: the menu hides what a role may not use, and every service method checks the permission again, so the logic is safe even if the screen is wrong.

الأساس: اللي شايل المشروع كله

الجزء ده مالوش سطر لوحده في طلبات الكلية، بس من غيره مفيش حاجة تشتغل. هو: فتح البرنامج، الحفظ في الملفات، الشاشة الرئيسية والقايمة، الكلاسات المشتركة اللي كل الشاشات بتورث منها، حساب أقصر طريق، الخريطة، ولوحة البيانات (Dashboard).

المستخدم بيشوف إيه

    protected abstract T parse(String[] fields);   // one line of the file  -> one object
    protected abstract String[] format(T item);    // one object -> one line of the file

    public void load() { ... }    // read every line, call parse() for each
    public void save(T item) { ... }  // add or replace, then rewrite the file safely
}

public class StationRepository extends FileRepository<Station> {

حساب أقصر طريق (RoutePlanner)

تخيل إنك رميت حجر في مية عند محطة حلوان. الموجة الأولى بتوصل لكل المحطات اللي جنبها على طول (محطة واحدة). الموجة التانية لكل اللي بعدهم (محطتين)، وهكذا. أول موجة توصل لجامعة القاهرة = أقصر طريق. الطريقة دي اسمها Breadth-First Search.

  • محطتين يعتبروا "جيران" لو جنب بعض على أي خط.
  • بعد ما يلاقي الطريق، بيقسمه لأجزاء: كل جزء على خط واحد، والتغيير بيحصل في المحطة اللي فيها خطين (زي السادات).
  • لو مفيش طريق خالص بيرجع رسالة واضحة: "No route between ...".
The route planner uses breadth-first search: it visits all stations one stop away, then two stops away, so the first time it reaches the destination it has the route with the fewest stops.

public abstract class User extends Entity {
    private final String username;                 // final + no setter = can never change
    public abstract Set<Permission> getPermissions();   // every role must answer this

    public boolean can(Permission permission) {
        return getPermissions().contains(permission);
    }
}

public class StationSupervisor extends TicketAgent {
    @Override
    public Set<Permission> getPermissions() {
        Set<Permission> permissions = super.getPermissions();  // everything a ticket agent has
        permissions.add(Permission.REFUND_TICKETS);             // ... plus refunds
        return permissions;
    }
}
abstract ... getPermissions() = كل دور لازم يجاوب على السؤال ده بطريقته.
can(...) = بيسأل الدور عن صلاحياته ويشوف الصلاحية المطلوبة موجودة ولا لأ. مش بيعرف ولا محتاج يعرف هو بيكلم أدمن ولا موظف — ده الـ polymorphism.
super.getPermissions() = "هات صلاحيات أبويا" (موظف الشباك)، وبعدين بنزود عليها.

الحارس على كل باب

public void require(Permission permission) {
    if (!can(permission)) {
        throw new AccessDeniedException("You do not have permission to do this.");
    }
}

كل method في كل service في المشروع بيبدأ بسطر زي session.require(Permission.MANAGE_USERS). ده "الحارس" اللي بيرفض أي حد مش مسموح له، حتى لو الشاشة غلطت.

الباسورد بيتحفظ إزاي؟

عمرنا ما بنحفظ الباسورد نفسه. بنحطه في "خلاط" رياضي (اسمه PBKDF2) بيطلع كلام ملخبط، والخلاط ده مينفعش يترجع لورا. ولما حد يدخل، بنحط الباسورد اللي كتبه في نفس الخلاط ونقارن النتيجتين.

وكمان بنضيف لكل مستخدم "ملح" (salt) عشوائي قبل الخلط، فلو اتنين ليهم نفس الباسورد، الكلام الملخبط بتاعهم بيطلع مختلف.

We never store passwords. We store a salted PBKDF2 hash; at login we hash what was typed with the same salt and compare the two hashes.

  • مينفعش توقف حسابك أنت.

public class Line extends Entity {
    private List<Station> stations = new ArrayList<>();

    public List<Station> getStations() {
        return Collections.unmodifiableList(stations);   // read-only copy for the outside
    }

    public void setStations(List<Station> stations) {
        List<Station> copy = new ArrayList<>();
        for (Station station : stations) {
            if (copy.contains(station)) {
                throw new ValidationException("A station can appear only once on a line");
            }
            copy.add(station);
        }
        this.stations = copy;
    }
}
getStations() = بيدّي اللي بره نسخة "للقراية بس". محدش يقدر يزود محطة من وراه.
setStations(...) = الطريقة الوحيدة لتغيير المحطات، وبتتأكد إن مفيش محطة متكررة. ده encapsulation.

ليه "السادات" محطة تبادل؟

محطة السادات هي أوبجكت واحد، والخط الأول والخط التاني الاتنين ماسكين نفس الأوبجكت ده في قوايمهم. فالبرنامج يعد: المحطة دي على كام خط؟ لو اتنين أو أكتر يبقى Interchange. مش متخزنة كمعلومة لوحدها، فعمرها ما تبقى غلط.

ولو غيرت اسم المحطة، بيتغير في كل الخطوط في نفس اللحظة، لأنهم كلهم بيشاوروا على نفس المحطة. ده اسمه Aggregation: الخط "بيجمع" محطات ليها حياة لوحدها.

رقم القطر: ليه فيه اتنين؟

الكلية عايزة الأدمن "يعدل الـ Train ID". بس عندنا قاعدة إن رقم أي سجل (id) مبيتغيرش أبدًا، لأن الرحلات بتشاور عليه. فالقطر عنده:

  • id مثل TRN-001: داخلي، ثابت، الرحلات بتشاور عليه.
  • code مثل T-101: ده اللي الموظفين بيشوفوه باسم "Train ID" ويقدروا يعدلوه.

القواعد

  • اسم المحطة مايتكررش (حتى لو الاختلاف حروف كبيرة وصغيرة أو مسافات).
  • محطة على خط مينفعش تتمسح: "اشيلها من الخط الأول أو اقفلها". ومحطة اتباع لها تذاكر قبل كده مينفعش تتمسح.
  • الخط لازم يبقى فيه محطتين على الأقل، ومفيش محطة مرتين على نفس الخط، واللون شكله زي #1A2B3C.
  • Train ID مايتكررش وبيتحفظ بحروف كبيرة، والسعة من ١ لـ ٣٠٠٠.
  • قطر عنده رحلات لسه مخلصتش مينفعش يدخل صيانة. وقطر اشتغل قبل كده مينفعش يتمسح ("خليه Retired").
  • خط عليه رحلات مينفعش يتمسح.
  • لو أي قاعدة اترفضت، مفيش حاجة بتتغير خالص.

public boolean overlaps(LocalDateTime otherDeparture, LocalDateTime otherArrival, int gapMinutes) {
    return departure.isBefore(otherArrival.plusMinutes(gapMinutes))
        && otherDeparture.isBefore(getEffectiveArrival().plusMinutes(gapMinutes));
}
departure.isBefore(...) = رحلتي بتبدأ قبل ما التانية تخلص (+ وقت الراحة)؟

public List<Trip> findConflicts(Train train, LocalDateTime departure, LocalDateTime arrival, String ignoreTripId) {
    List<Trip> conflicts = new ArrayList<>();
    for (Trip other : trips.findByTrain(train)) {                 // only trips of the SAME train
        if (other.getId().equals(ignoreTripId) || other.getStatus() == TripStatus.CANCELLED) {
            continue;                                              // skip itself and cancelled trips
        }
        if (other.overlaps(departure, arrival, TURNAROUND_GAP_MINUTES)) {
            conflicts.add(other);
        }
    }
    return conflicts;
}

public abstract class Ticket extends Entity {
    private final double baseFare;           // the full price for this many stops

    public abstract double discountRate();    // each type gives its own answer

    public double getFare() {
        return Money.round(baseFare * (1 - discountRate()));
    }
}

public class StudentTicket extends Ticket {
    @Override
    public double discountRate() {
        return 0.50;                            // half price
    }
}
getFare() متكتبة مرة واحدة في الأب: السعر الأساسي × (١ − الخصم).
discountRate() abstract: كل نوع بيقول خصمه. العادية 0، الطالب 0.50، كبير السن 0.30.
مثال: ٢٢ محطة = ١٥ جنيه أساسي. عادية = ١٥، طالب = ٧٫٥٠، كبير سن = ١٠٫٥٠.
البيع والتقارير ولوحة البيانات بيقولوا ticket.getFare() وخلاص، من غير ما يعرفوا النوع. ده الـ polymorphism.
getFare is written once; each ticket subclass answers discountRate differently. Code that holds any Ticket just calls getFare and gets the right price.

  • مين يقدر يرجّع، وإمتى؟المشرف والأدمن، لتذكرة متستخدمتش واتباعت النهارده، بالفلوس كاملة.
  • التذكرة المرجعة بتتمسح؟لأ، بتفضل بحالة Refunded ومين رجعها وإمتى، وتقرير الإيرادات بيخصمها في يوم الإرجاع.

جرّب بنفسك

  • ادخل agent، بيع تذكرتين من حلوان لجامعة القاهرة، وبص على آخر سطرين في data/tickets.txt. اعمل Validate لواحدة مرتين.
  • ادخل supervisor ورجّع التانية. حاول ترجّعها تاني واقرا الرسالة.
الجزء ٦

التقارير

طلبات الكلية في جزءك (Module 4):

  • 4a — الأدمن يعمل تقارير عن الرحلات حسب التاريخ والخط والحالة.
  • 4b — الأدمن يشوف عدد التذاكر المبيوعة لكل مشوار.
  • 4c — النظام يلخص الإيرادات في فترة يختارها.

المستخدم بيشوف إيه

  • في كل تقرير: من تاريخ لتاريخ (افتراضيًا آخر ٧ أيام)، زرار Generate، وزرار Export CSV اللي بيحفظ التقرير ملف يفتح في Excel.
  • Trip report: فلتر بالخط والحالة، ٤ مربعات بعدد كل حالة، ورسم دايرة (pie chart) بنفس ألوان الحالات، والجدول.
  • Ticket report: عدد التذاكر لكل مشوار، الأكتر فوق، ورسم أعمدة لأكتر ٨ مشاوير.
  • Revenue report: المبيعات، المرتجع، وصافي الإيراد بأرقام كبيرة، ورسم أعمدة لصافي كل يوم، وجدول بآخره سطر "Total".
  • لو مفيش بيانات في الفترة: "No data for these dates."

Report is abstract with getColumns and getRows; exportCsv is written once and works for every report because it only uses those two methods.

الإيرادات بتتحسب إزاي؟ (4c)

  • بنعمل صف لكل يوم في الفترة، حتى الأيام اللي محصلش فيها حاجة (تطلع أصفار).
  • كل تذكرة: سعرها بيتحسب مبيعات في يوم بيعها — حتى لو اترجعت بعد كده.
  • ولو اترجعت: سعرها بيتحسب مرتجع في يوم الإرجاع.
  • الصافي = المبيعات − المرتجع.

مثال: يوم فيه ٥ تذاكر بـ ٣٦ جنيه، وواحدة منهم اترجعت بـ ٨ جنيه: مبيعات ٣٦، مرتجع ٨، صافي ٢٨.

القواعد

  • لازم تاريخ بداية ونهاية، والبداية مينفعش تبقى بعد النهاية.
  • يوم النهاية بيتحسب كله (تذكرة الساعة ١١:٥٩ بالليل داخلة).
  • الرحلة بتتحسب في يوم طلوعها.
  • في تقرير التذاكر، التذاكر المرجعة مش بتتعد، ومن A لـ G غير من G لـ A.
  • الكلام اللي فيه فاصلة أو علامة تنصيص في الـ CSV بيتحط بين علامات تنصيص عشان Excel يفهمه صح.
  • الأدمن بس يقدر يعمل تقارير.

الـ OOP في جزءك

Abstraction

Report abstract وفيه getColumns وgetRows abstract: كل تقرير لازم يقدمهم.

Polymorphism

exportCsv واحدة لكل التقارير، والجدول في الشاشة بيتبني بنفس الطريقة لأي تقرير.

Inheritance

التلات تقارير بيورثوا Report (التحقق من التواريخ والتصدير). والتلات شاشات بيورثوا ReportScreen.

Encapsulation

الصفوف (JourneyCount، DayRevenue) بتتعدل بس من جوه التقرير نفسه، وبره بيقروها بالـ getters.

Relationships

التقرير composition مع صفوفه: هو اللي بيعملها وهي بتاعته. وبيستخدم الرحلات والتذاكر من غير ما يملكها.

لو الدكتور سألك

  • ليه Report abstract؟كل التقارير ليها فترة وتصدير، بس كل واحد أعمدته وصفوفه مختلفة. الـ abstract methods بتجبر كل تقرير يقدمهم.
  • إزاي تصدير واحد بيشتغل مع ٣ تقارير؟لأنه بيستخدم بس getColumns و getRows، وكل تقرير عنده الاتنين. ده polymorphism.
  • ليه تقرير الإيرادات بيحسب بيع التذكرة اللي اترجعت؟الفلوس دخلت يومها فعلًا. الإرجاع حدث تاني في يومه. والصافي = المبيعات − المرتجع، فكل يوم أرقامه صح.
    A sale counts on the day it was sold and a refund on the day it was refunded; net revenue is sales minus refunds.
  • ليه تقرير التذاكر مبيعدش المرجعة؟لأنه بيعد المشاوير اللي اتباعت، والمرجعة بيعها اتلغى.
  • لو مفيش بيانات في الفترة؟الجدول فاضي ومكتوب "No data for these dates."، والتصدير بيطلع سطر العناوين بس.
  • الرسومات اتعملت إزاي؟بالـ PieChart و BarChart بتوع JavaFX نفسها، بتتملا من كائنات التقرير.
  • لو عايز تضيف تقرير رابع؟كلاس يورث Report ويكتب getColumns و getRows، وشاشة تورث ReportScreen، وزرار في القايمة. التصدير والجدول بيشتغلوا لوحدهم.

جرّب بنفسك

  • ادخل admin، افتح Trip report واختار الحالة Delayed واضغط Generate. بعدين خلي "From" بعد "To" واقرا الرسالة.
  • اعمل Export CSV لتقرير الإيرادات وافتحه في Excel أو Notepad.

العرض في ٥ دقايق

  1. agent: القايمة قصيرة (الصلاحيات). بيع تذكرة حلوان ← جامعة القاهرة، ووري الطريق والتغيير في السادات والسعر. افتح tickets.txt.

  3. controller: اعمل رحلة متعارضة واتفرج عليها بتترفض، وأخّر رحلة.
  4. admin: بحث في المحطات وإضافة محطة، الخطوط، تقرير الإيرادات، والموظفين.
  5. اختم بالخريطة والطريق منوّر.
